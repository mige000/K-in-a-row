4a. Everything happens inside the function minimax() in reidunt_KInARow.py. Alpha and beta are function arguments, each call to minimax keeps its own local alpha/beta variables, from the values its caller passed in. Inside the loop over candidate moves, after each child's value is returned, the current node updates its own bound (alpha = max(alpha, best_val) for a maximizing node, beta = min(beta, best_val) for a minimizing node) and checks if alpha >= beta: cutoff; break. The break exits the for-loop over moves, so any remaining sibling moves in that list are never explored. Propagating back up happens through the return value. The parent passes its (possibly already tightened) alpha/beta into every child call it makes in its own loop, so a child's tightened bound is visible to the next child's entire subtree, and a cutoff anywhere in that subtree then bubbles back up as soon as that recursive call returns.

4b. Using depth-4 search from the Tic-Tac-Toe initial state: 

                    static evaluations
  Alpha-Beta OFF            336
  Alpha-Beta ON             123

Alpha-beta reduced the number of static evaluation from 336 to 123, so we saved 213 evaluations, or a 63.4% reduction. while both searches picked the identical move, (1,1), with the identical backed-up score (0.0333...), confirming the pruning did not change the result, only the work needed to find it.

4c. Conceptual question — correctness of pruning. At any max node, alpha is the best value the maximizer has already been guaranteed to be able to achieve somewhere else in the tree, on the path explored so far; at any min node, beta is the analogous guarantee already available to the minimizer. When exploring a min node's children and one child's value is found to be <= alpha, that min node's final backed-up value (which only ever gets smaller or equal as more children are explored, since a min node takes the minimum over its children) can never rise back above that child's value. So the min node's value is already known to be at most as good for the maximizer as an alternative the maximizer can obtain elsewhere — which means the maximizer will never choose the move leading into this min node regardless of what its remaining, unexplored children turn out to be. Pruning those children is therefore safe: exploring them could only ever lower (or leave unchanged) a value that is already not going to be selected, so it cannot change the move chosen at the root. The symmetric argument holds for max nodes and beta.

    and report the numerical score your static_eval returned for it.

5c. Limitations
    Describe at least one type of board position where your static_eval
    is likely to give a misleading score, and explain why.

5a. Feature design. static_eval (in yourID_KInARow.py) scans every possible window of length k on the board in all four line directions (horizontal, vertical, and both diagonals). For each window it counts X's and O's inside it. A window containing both X and O can never become a win for either player, so it contributes 0. A window containing a forbidden square ('-') is likewise dead and contributes 0. A window containing only one player's tokens contributes ±10^count (positive for X, negative for O) — an exponential, not linear, function of how many tokens that player already has in the window. The intuition is that a line with k-1 tokens and an open square is an immediate threat that should dominate the score far more than two separate lines with one token each, and only an exponential weighting (rather than, say, a count or a sum) produces that kind of dominance. A small secondary term adds ±0.1 per token scaled by closeness to the board's center, mainly to break ties between otherwise-equal positions in favor of central play.

5b. Concrete example. From an actual agent-vs-RandomPlayer Tic-Tac-Toe game (reproduced via a short script that replays make_move turn by turn and prints static_eval after every move), after X's second move the board was: 

  O  .  .
  .  X  X
  .  .  .

(O to move next.) static_eval returned 110.1167. This is the right order of magnitude for this position: X has two tokens in the open middle row, (1,1) and (1,2), with (1,0) still blank — a single window (the middle row) contributes 10^2 = 100 to the score. The small remainder (10.1167) comes from the centrality bonus for X's two central-ish squares plus O's single corner token working against it. The dominant 100-point contribution correctly reflects that X is one move away from winning via that row if O does not block (1,0), which is exactly the kind of near-complete-line threat the exponential weighting is designed to surface.

5c. Limitations. The window-sum approach has no notion of a "double threat" or fork: it simply adds up every window's contribution independently, so a position where two different near-complete lines for X happen to share their only blocking square (meaning O can kill both lines with a single move) is scored the same as if those two lines required two separate blocking moves. In reality the latter is a much stronger position for X (O cannot stop both), but static_eval cannot distinguish "two threats, one shared escape square for the opponent" from "two threats, two independent escape squares" — both simply sum the two windows' weights. A more accurate evaluator would need to reason about which empty squares are shared between multiple live lines, not just score each line in isolation.

6a. Game-state relevance. Our agent picks what to say using _choose_bucket() in reidunt_KInARow.py, which is a set of IF-THEN rules that look at the current board and the search result every turn. It starts by checking whether it's move 1, and if so it uses an opening line. Next it checks whether the move it just picked wins right away (using winTesterForK) so Kitti can gloat, or whether the backed-up minimax score says she's going to lose no matter what, in which case she gets dramatic about it. To notice the opponent's last move, it runs one extra static_eval on the board from before our move and compares that to self.last_my_eval, the score after our previous move. A big drop means the opponent's move hurt us, and Kitti reacts to it. It also looks at how hard the search worked (max_depth_reached_this_turn and time_elapsed_this_turn), and if the search went deep or took a while it uses a "thought really hard about that" line. If none of those apply, it looks at how big the current eval is and puts the position into a winning, building, danger, or quiet band. Each of these conditions maps to a named bucket of lines written for the persona, and the agent picks one line from whichever bucket matches.

That bucket logic decides the situation, but it isn't always what decides the actual words. When Gemini is available, we still run _choose_bucket() first and use its line as the fallback, but before falling back we hand the model the real board (as text), our real eval number, and the opponent's actual last remark, and ask it to react to that directly instead of just reading out the bucket's hand-written line. So game-state relevance happens two ways now: the bucket decides which mood applies, and separately, whenever Gemini responds in time, the model is reacting to the board and score that turn instead of a pre-written line for that mood.

Because the log includes what the opponent said, Kitti can quote their actual words from key moments in the game.

The biggest bug we ran into came from a "win-shortcut" we added to minimax(). After generating the child state for a candidate move, it called winTesterForK on that child, and if the move won right away it returned an extreme score immediately instead of searching any deeper. This helps in real games because the search stops wasting time past a forced win, and the win gets valued as an actual win instead of whatever finite number static_eval would give it. We added it before re-running the autograder tests, and that's when the problem showed up.

The symptom was in autograder.py's T4 test, which runs plain minimax with no pruning to depth 2 using the special table-based evaluator. Our agent picked the correct move, but the leaf count was wrong. It made 9 static evaluations when the expected number was 12.

It took some digging to find the root cause. The test state (O,O,X / X,_,_ / _,_,X) actually has a real win inside the 2-ply search tree. X already has (0,2) and (2,2), so if O's first move leaves (1,2) open, X can play there and complete column 2. Our win-shortcut correctly caught this and returned early, which meant it skipped the evaluator call for that leaf. That's the right behavior for real play, but the autograder's count of 12 assumes every branch gets searched all the way to the depth limit with no early stopping. The autograder's own hint text confirmed this, saying the count does not depend on move ordering and that the special evaluation function should be called at every leaf.

To fix it, we added a self._check_wins flag. It's set to True in DEMO and COMPETITION modes and False whenever self.playing_mode == KAgent.AUTOGRADER, and the winTesterForK call in minimax() only runs when the flag is on. After that change, T4 reported exactly 12 leaf evaluations and T5 (alpha-beta) reported exactly 8, both matching the expected values. The win-shortcut still runs during actual games, where it's useful.

We also ran into trouble with the speed of the Gemini LLM we use for Kitti's dialogue. At first it timed out constantly, and when it did respond it could take anywhere from under a second to 145 seconds for the exact same kind of request. For a while, the only thing we had to show for it was the fallback working correctly: when the call times out or fails, the agent falls back to the IF-THEN lines from _choose_bucket() and KITTI_LINES/BUNNI_LINES, so Kitti and Bunni always have something to say and the game never stalls waiting on the API. That part worked, but it meant almost every turn used hand-written lines instead of generated ones.

We eventually tracked the slowness down to the model itself, not our code. We were calling gemini-flash-latest, which was pointing at a heavier model (gemini-3.8-flash), and that model kept hitting the free tier's request limit and server overload on Google's side, and the SDK was quietly retrying those overloaded calls in the background for up to two and a half minutes before giving up. Switching to gemini-flash-lite-latest fixed this issue. After that switch, repeated real calls through the agent came back in well under a second, consistently.

One other thing that looked like a bug at first but turned out not to be was in our test games between Kitti and Bunni on Cassini, it kept ending in draws, no matter who played which side. Since they have different playing styles (Bunni's defensive_bias), we expected that to show up as one of them winning more often. To check whether something was actually wrong, we ran Kitti against a plain copy of herself (no bias difference at all) and Bunni against a plain copy of herself, and those drew too, every time, at several different search depths. Kitti still beat RandomPlayer on Cassini easily (by turn 9). So the draws aren't a bug. We realized that two agents built on the same search and evaluation logic are just evenly matched enough to block each other at the depths we can search in time, even when one of them is tuned to be more defensive. If I were to explain alpha-beta pruning to a classmate, the most important thing I would tell them is that the bound you are pruning with is not a property of the subtree you're currently searching, it's a guarantee from somewhere else in the tree that the player who owns that bound already has. It's not saying that this subtree is bad, it's just saying that it doesn't matter whether this subtree is bad, because nobody would ever choose to go here anyway. Pruning makes the search faster because if you find a branch that cannot lead to a better outcome than what a player already has available, you don't need to keep exploring it.

Part I A: Child ordering by static evaluation

In DEMO and COMPETITION modes, _generate_moves_ordered builds the child state for every possible move and sorts the moves by the static_eval of that child before searching them. X is the maximizer, so its moves are sorted from highest to lowest, and O's moves are sorted from lowest to highest. The idea comes from a standard alpha beta result: if you search the best move first, the later moves are much more likely to get cut off by the current alpha or beta bound.

To measure it, extra_credit_benchmark.py runs the same 4 ply alpha beta search from the Cassini starting state with and without ordering. We used Cassini because its two handicap O's give the move generator something to work with right from move 1. 

              nodes visited   cutoffs (rate)     leaf evaluations
  baseline         3730       3197  (85.7%)           30920
  ordering         1097        984  (89.7%)            3309

Ordering cut the number of nodes visited by about 71%, from 3730 down to 1097, and the number of leaf evaluations by about 89%, from 30920 down to 3309. The cutoff rate per node also went up a little, from 85.7% to 89.7%. Both versions picked the same move, which is what we expected, since alpha beta gives the same answer no matter what order the moves are searched in.

What we learned: the tree got a lot smaller than we expected, but the moves didn't actually get faster in real time. Ordering means calling static_eval on every candidate at every internal node, which added 33018 extra evaluations in this test. Since static_eval checks every line of length k on the board, that extra work costs about as much as the leaf evaluations it saves. So the lesson for us was that the ordering step has to be cheap compared to the work it's trying to skip. Using the full static evaluator is a clear choice and it's what the assignment asked for, but to actually make moves faster we'd want something much cheaper for ordering, like a quick count of nearby pieces. Another option is caching the static evals so they don't get recomputed in overlapping parts of the tree, which is part of what Part I B does.

Part I B: Zobrist hashing

Zobrist hashing gives every (square, piece) pair on the board its own random 64 bit number, plus one number for "X to move" and one for "O to move." These get generated once in _init_zobrist when prepare learns the board size. To hash a state, _zobrist_hash XORs together the numbers for every occupied square and the number for whose turn it is. Since XOR doesn't care about order, two different move sequences that end up at the same board (a transposition) get the same hash. That lets us use a transposition table keyed by the hash, so the search can recognize a position it has already solved at this depth and reuse the stored result instead of searching it again.

Every table access goes through two small helpers, _tt_read and _tt_write, which keep three counters: writes (every time a node's backed up value gets stored), read attempts (every lookup, whether it finds something or not), and hits (lookups that found a stored entry). These show up in the AUTOGRADER mode stats dict as zobrist_table_num_entries_this_turn, zobrist_table_num_reads_this_turn, and zobrist_table_num_hits_this_turn. We only use a hit to skip the search directly when alpha beta pruning is off and the stored depth is at least as deep as the depth remaining. With pruning on, the stored value might only be a bound instead of the exact value, so reusing it could give the wrong answer. As the extra credit option describes, we also use stored values to help order children for Part I A. If a child's value is already in the table, we use that instead of calling static_eval again.

We measured it with the same 4 ply Cassini benchmark, with Zobrist hashing turned on: 

              tt writes   tt read attempts   tt hits (successful)
  zobrist        3730           3730               810
  both           1097          34115               383

The "zobrist" row has no Part I A ordering, so every node gets visited once and writes equal read attempts (3730 each). About 22% of those reads (810 out of 3730) found a transposition from somewhere else in the same search. The "both" row also has ordering on, so far fewer nodes get backed up and written (1097). But _ordering_eval adds a read attempt for every candidate at every node it visits, which brings the total reads to 34115, and 383 of those reused a stored value instead of calling static_eval again.

What we learned: transpositions happen a lot in this game, with hundreds of hits even in a short 4 ply search. That makes sense, since K in a Row has lots of different move orders that end up at the same board. But because our table is only safe for skipping the search when pruning is off, most of its value here came from helping with ordering instead of skipping nodes. A better version would store a flag with each entry saying whether the value is exact, a lower bound, or an upper bound. Then stored values could also be used safely to narrow the alpha beta window, not just to order children.

Part II: LLM assisted dialogue (Gemini, through Google's genai SDK)

prepare() only imports google.genai when self.playing_mode == KAgent.DEMO and utterances_matter is true, just like the assignment says. The import and client setup are wrapped in a try/except, so if anything fails, self._llm_client stays None. The API key is loaded from gemini_key_local.py first, which is listed in .gitignore, and then from the GEMINI_API_KEY environment variable if that file isn't there. We never hard code the key into the tracked file. Our repository is public on GitHub, and bots scrape keys out of public repos within minutes of a push. The gitignored local file means the agent still works without anyone setting up an environment variable when we hand it off directly (zip, email, or Canvas upload), and there's no risk of the key ending up in the public repo if someone accidentally adds every file with git. Every place that actually calls the API has its own try/except that returns None if anything goes wrong. When that happens, _generate_utterance falls back to the if/then lines in KITTI_LINES and BUNNI_LINES, so the agent never crashes and never gets stuck waiting on a request that hangs.

Getting this to actually work took a lot of debugging. We first built it with Claude (Anthropic's API), and when we decided to switch to Gemini so it would be easier to share on the free tier, the same design carried over. But once we tested with a real key, we hit three bugs before we got a single real response back.

The first bug was that Gemini's Flash models spend part of max_output_tokens on hidden "thinking" tokens before writing any visible text. With our small token limits (60 to 120), we were getting completely empty responses back with finish_reason: MAX_TOKENS and no text at all. We found this by looking at response.candidates[0] directly instead of trusting response.text.

The second bug was a 4 second timeout we set in http_options as a safety net. The API rejected it outright with the message "Manually set deadline 4s is too short. Minimum allowed deadline is 10s." Ten seconds is longer than we're willing to wait anyway, so we dropped it and used our own cutoff on our end instead.

The third bug was in that cutoff. We first built it with concurrent.futures.ThreadPoolExecutor, but by default it keeps the whole Python process from exiting until every task finishes, including slow calls we had already given up on. We switched to a plain threading.Thread(daemon=True) so an abandoned call can keep running in the background without holding anything up.

After those fixes, calls to the default Flash model alias (which pointed to Gemini 3.8 Flash) worked sometimes. One real success was "weak?? bold words for someone whose pieces i'm about to knock off the board (¬‿¬) just wait and see >:3", which reacted correctly to the opponent's taunt. But the timing was all over the place, anywhere from under a second to 145 seconds. During testing we also kept hitting the free tier's limit of 5 requests per minute (429 RESOURCE_EXHAUSTED) and actual server overload (503 UNAVAILABLE, "this model is currently experiencing high demand"). When we traced a raw exception, we found that the SDK's own automatic retry logic (built on the tenacity library) was quietly retrying overloaded requests with backoff inside our worker thread. That's what turned single calls into waits of several minutes.

What actually fixed it was switching to the Flash Lite model alias, which is lighter than the 3.8 Flash model the default alias pointed to, and removing the thinking_config parameter completely. That parameter caused a 400 INVALID_ARGUMENT error on the lite model. It also turned out the lite model doesn't use up the visible text budget on hidden thinking the way the bigger model did, so we didn't need a workaround. After that, repeated calls through the actual agent kept returning real, in character responses that fit the game, each in well under a second. For the opening, Kitti said "oh it's so on >:3 my paws are ready for this (￣▽￣)". When reacting to trash talk, she said "wait hold on, my paw slipped (￣▽￣) that eval is literally a lie omg". For the LLM enhanced story feature, she said "wait you actually almost had me back there (￣▽￣) but my paws are firmly on the lead now. 60/40 odds says i take this /ᐠ - ˕ -マ".

What we learned: writing the fallback code was necessary, but it wasn't enough on its own. If you stop debugging as soon as the agent seems to "work," a good fallback can hide a real problem you could have fixed. Our problem was never the key or the network. It was the parameters we chose and which model we picked. We found all three setup bugs (the thinking tokens, the rejected timeout, and the executor blocking exit) by purposely skipping the try/except so we could see the raw exceptions and response objects, not by reading the documentation first. We also think the model choice is a useful lesson in general. For a short, single turn persona line where nothing big is at stake, the smaller model wasn't just cheaper, it was also more reliable, so it wasn't really a trade off at all.
