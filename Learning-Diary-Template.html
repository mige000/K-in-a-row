4a. Everything happens inside the function minimax() in reidunt_KInARow.py. Alpha and beta are function arguments, each call to minimax keeps its own local alpha/beta variables, from the values its caller passed in. Inside the loop over candidate moves, after each child's value is returned, the current node updates its own bound (alpha = max(alpha, best_val) for a maximizing node, beta = min(beta, best_val) for a minimizing node) and checks if alpha >= beta: cutoff; break. The break exits the for-loop over moves, so any remaining sibling moves in that list are never explored. Propagating back up happens through the return value. The parent passes its (possibly already tightened) alpha/beta into every child call it makes in its own loop, so a child's tightened bound is visible to the next child's entire subtree, and a cutoff anywhere in that subtree then bubbles back up as soon as that recursive call returns.

4b. Using depth-4 search from the Tic-Tac-Toe initial state: 

                    static evaluations
  Alpha-Beta OFF            336
  Alpha-Beta ON             123

Alpha-beta reduced the number of static evaluation from 336 to 123, so we saved 213 evaluations, or a 63.4% reduction. while both searches picked the identical move, (1,1), with the identical backed-up score (0.0333...), confirming the pruning did not change the result, only the work needed to find it.

4c. Conceptual question — correctness of pruning. At any max node, alpha is the best value the maximizer has already been guaranteed to be able to achieve somewhere else in the tree, on the path explored so far; at any min node, beta is the analogous guarantee already available to the minimizer. When exploring a min node's children and one child's value is found to be <= alpha, that min node's final backed-up value (which only ever gets smaller or equal as more children are explored, since a min node takes the minimum over its children) can never rise back above that child's value. So the min node's value is already known to be at most as good for the maximizer as an alternative the maximizer can obtain elsewhere — which means the maximizer will never choose the move leading into this min node regardless of what its remaining, unexplored children turn out to be. Pruning those children is therefore safe: exploring them could only ever lower (or leave unchanged) a value that is already not going to be selected, so it cannot change the move chosen at the root. The symmetric argument holds for max nodes and beta.

    and report the numerical score your static_eval returned for it.

5c. Limitations
    Describe at least one type of board position where your static_eval
    is likely to give a misleading score, and explain why.

5a. Feature design. static_eval (in yourID_KInARow.py) scans every possible window of length k on the board in all four line directions (horizontal, vertical, and both diagonals). For each window it counts X's and O's inside it. A window containing both X and O can never become a win for either player, so it contributes 0. A window containing a forbidden square ('-') is likewise dead and contributes 0. A window containing only one player's tokens contributes ±10^count (positive for X, negative for O) — an exponential, not linear, function of how many tokens that player already has in the window. The intuition is that a line with k-1 tokens and an open square is an immediate threat that should dominate the score far more than two separate lines with one token each, and only an exponential weighting (rather than, say, a count or a sum) produces that kind of dominance. A small secondary term adds ±0.1 per token scaled by closeness to the board's center, mainly to break ties between otherwise-equal positions in favor of central play.

5b. Concrete example. From an actual agent-vs-RandomPlayer Tic-Tac-Toe game (reproduced via a short script that replays make_move turn by turn and prints static_eval after every move), after X's second move the board was: 

  O  .  .
  .  X  X
  .  .  .

(O to move next.) static_eval returned 110.1167. This is the right order of magnitude for this position: X has two tokens in the open middle row, (1,1) and (1,2), with (1,0) still blank — a single window (the middle row) contributes 10^2 = 100 to the score. The small remainder (10.1167) comes from the centrality bonus for X's two central-ish squares plus O's single corner token working against it. The dominant 100-point contribution correctly reflects that X is one move away from winning via that row if O does not block (1,0), which is exactly the kind of near-complete-line threat the exponential weighting is designed to surface.

5c. Limitations. The window-sum approach has no notion of a "double threat" or fork: it simply adds up every window's contribution independently, so a position where two different near-complete lines for X happen to share their only blocking square (meaning O can kill both lines with a single move) is scored the same as if those two lines required two separate blocking moves. In reality the latter is a much stronger position for X (O cannot stop both), but static_eval cannot distinguish "two threats, one shared escape square for the opponent" from "two threats, two independent escape squares" — both simply sum the two windows' weights. A more accurate evaluator would need to reason about which empty squares are shared between multiple live lines, not just score each line in isolation.

6a. Game-state relevance. Our agent picks what to say using _choose_bucket() in reidunt_KInARow.py, which is a set of IF-THEN rules that look at the current board and the search result every turn. It starts by checking whether it's move 1, and if so it uses an opening line. Next it checks whether the move it just picked wins right away (using winTesterForK) so Kitti can gloat, or whether the backed-up minimax score says she's going to lose no matter what, in which case she gets dramatic about it. To notice the opponent's last move, it runs one extra static_eval on the board from before our move and compares that to self.last_my_eval, the score after our previous move. A big drop means the opponent's move hurt us, and Kitti reacts to it. It also looks at how hard the search worked (max_depth_reached_this_turn and time_elapsed_this_turn), and if the search went deep or took a while it uses a "thought really hard about that" line. If none of those apply, it looks at how big the current eval is and puts the position into a winning, building, danger, or quiet band. Describe points of difficulty you encountered and how you resolved

The biggest bug we ran into came from a "win-shortcut" we added to minimax(). After generating the child state for a candidate move, it called winTesterForK on that child, and if the move won right away it returned an extreme score immediately instead of searching any deeper. This helps in real games because the search stops wasting time past a forced win, and the win gets valued as an actual win instead of whatever finite number static_eval would give it. We added it before re-running the autograder tests, and that's when the problem showed up.

The symptom was in autograder.py's T4 test, which runs plain minimax with no pruning to depth 2 using the special table-based evaluator. Our agent picked the correct move, but the leaf count was wrong. It made 9 static evaluations when the expected number was 12.

It took some digging to find the root cause. The test state (O,O,X / X,_,_ / _,_,X) actually has a real win inside the 2-ply search tree. X already has (0,2) and (2,2), so if O's first move leaves (1,2) open, X can play there and complete column 2. Our win-shortcut correctly caught this and returned early, which meant it skipped the evaluator call for that leaf. That's the right behavior for real play, but the autograder's count of 12 assumes every branch gets searched all the way to the depth limit with no early stopping. The autograder's own hint text confirmed this, saying the count does not depend on move ordering and that the special evaluation function should be called at every leaf.

To fix it, we added a self._check_wins flag. It's set to True in DEMO and COMPETITION modes and False whenever self.playing_mode == KAgent.AUTOGRADER, and the winTesterForK call in minimax() only runs when the flag is on. After that change, T4 reported exactly 12 leaf evaluations and T5 (alpha-beta) reported exactly 8, both matching the expected values. The win-shortcut still runs during actual games, where it's useful.

We also ran into real trouble with the speed of the Gemini LLM we use for Kitti's dialogue. At first it timed out constantly, and even when it did respond it could take anywhere from under a second to 145 seconds for the exact same kind of request. For a while, the only thing we had to show for it was the fallback working correctly: when the call times out or fails, the agent falls back to the IF-THEN lines from _choose_bucket() and KITTI_LINES/BUNNI_LINES, so Kitti and Bunni always have something to say and the game never stalls waiting on the API. That part worked, but it meant almost every turn used hand-written lines instead of generated ones, which wasn't really the point of the extra credit.

We eventually tracked the slowness down to the model itself, not our code. We were calling gemini-flash-latest, which was pointing at a heavier model (gemini-3.8-flash), and that model kept hitting the free tier's request limit and genuine server overload on Google's side, and the SDK was quietly retrying those overloaded calls in the background for up to two and a half minutes before giving up. Switching to gemini-flash-lite-latest fixed it outright — no extra workaround needed, it was just a lighter, more available model. After that switch, repeated real calls through the actual agent came back in well under a second, consistently. Section 11 has the full debugging story and the real lines that came back once this was fixed.

One other thing that looked like a bug at first but turned out not to be: our test games between Kitti and Bunni on Cassini kept ending in draws, no matter who played which side. Since they have different playing styles (Bunni's defensive_bias), we expected that to show up as one of them winning more often. To check whether something was actually wrong, we ran Kitti against a plain copy of herself (no bias difference at all) and Bunni against a plain copy of herself, and those drew too, every time, at several different search depths. Kitti still beat RandomPlayer on Cassini easily (by turn 9). Implementing iterative deepening under a wall-clock budget changed how I think about game-tree search: instead of "minimax to depth N," it is more natural to think of it as an anytime process that produces an improving sequence of answers, where each depth's result is only trustworthy if that whole depth finished before the clock ran out (which is why the agent only adopts a depth's result after that depth's top-level call returns, catching a timeout exception rather than trying to salvage a half-finished depth). The surprising part was how much a single optimization (the win-shortcut in Section 7) could clash with a grading reference's implicit assumptions — "correct and fast" and "matches the expected leaf count" turned out to be two different properties, and only one of them was actually being tested.

The most useful connection to make is to the alpha-beta measurement in Section 11 (Extra Credit): fewer nodes visited is not automatically faster in wall-clock time if the per-node work (here, calling static_eval to order children) is expensive relative to what it saves. That is the same lesson taught more abstractly in discussions of asymptotic complexity vs. real performance — Big-O node counts and actual runtime can diverge once you account for the constant factors.

If I were explaining alpha-beta to a classmate who had not implemented it yet, the one thing I would say is: the bound you are pruning with (alpha at a max node, beta at a min node) is not a property of the subtree you're currently searching — it is a guarantee from somewhere else in the tree that the player who owns that bound already has in hand. You're not saying "this subtree is bad"; you're saying "it doesn't matter whether this subtree is bad, because nobody would ever choose to go here anyway."

Part I-A: Child ordering by static evaluation

In DEMO/COMPETITION modes, _generate_moves_ordered builds the child state for every candidate move and sorts the candidates by static_eval of that child before recursing: descending for X (the maximizer, so the move most favorable to X is tried first) and ascending for O. The intent is the classic alpha-beta result that searching the best move first maximizes the chance that later siblings can be cut off by the current alpha/beta bound.

Measurement. extra_credit_benchmark.py runs a fixed 4-ply alpha-beta search from the Cassini initial state (chosen because its two handicap O's give the candidate-restricted move generator something to work with from move 1) with and without this ordering: 

              nodes visited   cutoffs (rate)     leaf evaluations
  baseline         3730       3197  (85.7%)           30920
  ordering         1097        984  (89.7%)            3309

Ordering by static eval cut the number of search-tree nodes visited by about 71% (3730 → 1097) and the number of true leaf evaluations by about 89% (30920 → 3309), while the per-node cutoff rate also rose slightly (85.7% → 89.7%). Both configurations picked the same move, as expected since alpha-beta is exact regardless of ordering.

What I learned. The tree-size reduction was far larger than I expected, but it did not translate into a faster wall-clock move in this implementation: ordering requires computing static_eval for every candidate at every internal node it visits (33018 extra "ordering" evaluations here), and because static_eval scans every k-length line on the board, that overhead is roughly as expensive as the leaf evaluations it saves. The lesson is that move-ordering heuristics need to be cheap relative to the thing they are trying to avoid recomputing — a full static evaluator is a sound, pedagogically clear choice (and is what the assignment asked for), but a production engine would want a much cheaper ordering signal (e.g. a shallow pattern/neighbor count) to actually convert the smaller tree into a wall-clock win, or cache the static evals so they are not recomputed on overlapping subtrees (see Part I-B).

Part I-B: Zobrist hashing

Zobrist hashing assigns one independent random 64-bit number to every (square, piece) pair on the board (plus one for "it is X's turn" and one for "it is O's turn"), computed once in _init_zobrist when prepare learns the board size. A state's hash is the XOR of the numbers for every occupied square plus the side-to-move number (_zobrist_hash). XOR makes the hash order-independent and cheap to verify, and two different move orders that reach the same board (a transposition) hash identically, so a transposition table keyed by this hash lets the search recognize "I have already solved this position at this depth" and reuse the stored result instead of re-searching it.

Every table access goes through two small helpers, _tt_read/_tt_write, which keep three counters: writes (every time a node's backed-up value is stored), read attempts (every lookup, hit or miss), and successful attempts/hits (lookups that found a previously stored entry). Those three numbers are returned in the AUTOGRADER-mode stats dict as zobrist_table_num_entries_this_turn, zobrist_table_num_reads_this_turn, and zobrist_table_num_hits_this_turn. A hit is only used to short-circuit the search directly when not using alpha-beta pruning and the cached depth is at least the depth remaining (otherwise the cached value could be a pruned bound rather than the exact backed-up value, and reusing it could be unsound); as the extra-credit option notes, cached values are also used to help order children (Part I-A) — a child whose value is already in the table is scored from the cache instead of calling static_eval again.

Measurement. Same 4-ply Cassini benchmark, with Zobrist hashing turned on: 

              tt writes   tt read attempts   tt hits (successful)
  zobrist        3730           3730               810
  both           1097          34115               383

With plain minimax node ordering ("zobrist" row, no I-A ordering), every node is visited exactly once per the usual tree shape, so writes equal read attempts (3730 each) and about 22% of reads (810/3730) found a transposition from elsewhere in the same search. Combined with I-A ordering ("both" row), far fewer nodes are backed up and written (1097), but _ordering_eval adds a read attempt for every candidate at every node it visits (34115 reads total), of which 383 were reused instead of calling static_eval again.

What I learned. Transpositions are genuinely common in this game even over a short 4-ply search (hundreds of hits), which matches the intuition that K-in-a-Row has many move orders reaching the same board. However, because my transposition table is only safe to use for a direct cutoff in the no-pruning case, most of its value here came from the ordering use case rather than the raw node-skipping use case — a more sophisticated implementation would store alpha/beta bound flags (exact/lower/upper) with each entry so cached values could also be used safely to narrow the window under alpha-beta pruning, not just to order children.

Part II: LLM-assisted dialog (Gemini, via the google-genai SDK)

prepare() only imports google.genai when self.playing_mode == KAgent.DEMO and utterances_matter is true, exactly as the assignment specifies, and the import plus client construction are wrapped in a try/except that leaves self._llm_client as None on any failure. The API key is resolved from gemini_key_local.py (a file listed in .gitignore) first, then the GEMINI_API_KEY environment variable — never hard-coded directly into this tracked file. Why: this repository is public on GitHub, and a hard-coded key in a public repo gets scraped by bots within minutes of pushing. A gitignored local file gets the same "it just works, no env var setup" convenience the assignment wants for a direct handoff (zip, email, Canvas upload) to a specific person, without ever risking that key reaching the public repo by an accidental git add -A. Every call site that actually talks to the API is wrapped in its own try/except Exception and returns None on any failure, at which point _generate_utterance falls back to the rule-based KITTI_LINES/BUNNI_LINES bank, so the agent never raises and never stalls waiting on a hung request.

Getting it actually working took real debugging, not just plumbing. I originally built this against Claude (Anthropic's API); when asked to switch to Gemini for easier free-tier sharing, the same design carried over, but live testing against a real key surfaced three real bugs before a single genuine response came through:

  • Gemini's Flash models spend part of max_output_tokens on hidden "thinking" tokens before writing visible text; at our small token budgets (60-120) this silently returned completely empty responses (finish_reason: MAX_TOKENS, no visible text at all). Diagnosed by inspecting response.candidates[0] directly instead of trusting response.text.
  • A custom 4-second http_options timeout I added as a safety net was rejected outright by the API itself: "Manually set deadline 4s is too short. Minimum allowed deadline is 10s." — longer than we're willing to wait regardless, so I dropped it in favor of our own client-side cutoff.
  • That client-side cutoff was first built with concurrent.futures.ThreadPoolExecutor, but its default shutdown behavior blocks the whole Python process from exiting until every submitted task finishes — including an abandoned, still-running slow call. Switched to an explicit threading.Thread(daemon=True) so an abandoned call can keep running in the background without blocking anything.

After those fixes, calls to the default model alias (gemini-flash-latest, which resolved to gemini-3.8-flash) sometimes worked (one genuine success: "weak?? bold words for someone whose pieces i'm about to knock off the board (¬‿¬) just wait and see >:3", correctly reacting to an opponent's taunt) but were wildly inconsistent — anywhere from under a second to 145 seconds, and repeatedly hitting both the free tier's 5-requests-per-minute quota (429 RESOURCE_EXHAUSTED) and genuine server overload (503 UNAVAILABLE, "this model is currently experiencing high demand") during testing. Tracing a raw exception showed the SDK's own tenacity-based automatic retry logic was quietly retrying overloaded requests with backoff inside the worker thread, which is what turned single calls into multi-minute waits.

The actual fix: switching to gemini-flash-lite-latest (a lighter model than the "3.8 Flash" the default alias pointed to) and removing the thinking_config parameter entirely — it turned out to cause a 400 INVALID_ARGUMENT specifically on the lite model (it apparently doesn't take that parameter the same way), and empirically the lite model doesn't eat the visible-text budget on hidden thinking the way the heavier model did, so no workaround was even needed. After this change, repeated calls through the actual agent consistently returned genuine, in-character, context-aware responses in well under one second each: 

  "oh it's so on >:3 my paws are ready for this (￣▽￣)"           (opening)
  "wait hold on, my paw slipped (￣▽￣) that eval is literally a lie omg"  (reacting to trash talk)
  "wait you actually almost had me back there (￣▽￣) but my
   paws are firmly on the lead now. 60/40 odds says i take this /ᐠ - ˕ -マ"
                                                        (LLM-enhanced story feature)

What I learned. Writing the fallback-safety code was necessary but not sufficient — a graceful fallback can mask a real, fixable problem (ours was never a key or network issue; it was parameter choices and a model-selection trade-off) if you stop debugging as soon as the fallback makes the agent "work." The three infrastructure bugs (thinking tokens, the rejected timeout, the executor-blocks-exit issue) were all found by deliberately bypassing the try/except to look at raw exceptions and response objects, not by reading documentation first. I'd also flag the lite-vs-full-model choice as a transferable lesson: for a short, low-stakes, single-turn persona line, the "smaller" model was not just cheaper but also more reliable, not a trade-off at all.

Both are implemented as special cases checked before the ordinary IF-THEN bucket logic in _generate_utterance, matching against the opponent's exact last utterance (current_remark), case-insensitively. Everything else either of them says, including the many genuinely LLM-generated lines in the opening third of this game, is unscripted.

"Tell me how you did that": 

  ok so you asked for it lol (=^･ω･^=) for that move i looked at 129
  positions total, and 1,236 of those were leaf positions i actually
  scored. i got to depth 3 which was as deep as i was allowed to go
  (0.17s, i'm slow ok ;-;). i pruned 87 branches with alpha-beta
  cutoffs, which is basically me going "nope, already know that's
  worse" and swatting it away ^-^ i didn't even bother with my zobrist

  +760, so i was pretty sure about this one (￣▽￣)

Every number is read directly from this turn's real counters (num_nodes_visited_this_turn, num_leaf_evals_this_turn, max_depth_reached_this_turn, time_elapsed_this_turn, alpha_beta_cutoffs_this_turn, zobrist_table_num_hits_this_turn, best_score_this_turn/second_best_score_this_turn, the latter two collected via a one-shot flag, _collect_root_scores, that lets minimax() record every root child's exact backed-up value without changing the recursive algorithm itself). "What's your take on the game so far?" — this one did go through Gemini, since the model responded in time: 

  wait no way (・・?) i totally clawed my way back after move two! i'm
  betting on myself for this one (￣▽￣)
