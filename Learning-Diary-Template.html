4a. Everything happens inside the function minimax() in reidunt_KInARow.py. Alpha and beta are function arguments, each call to minimax keeps its own local alpha/beta variables, from the values its caller passed in. Inside the loop over candidate moves, after each child's value is returned, the current node updates its own bound (alpha = max(alpha, best_val) for a maximizing node, beta = min(beta, best_val) for a minimizing node) and checks if alpha >= beta: cutoff; break. The break exits the for-loop over moves, so any remaining sibling moves in that list are never explored. Propagating back up happens through the return value. The parent passes its (possibly already tightened) alpha/beta into every child call it makes in its own loop, so a child's tightened bound is visible to the next child's entire subtree, and a cutoff anywhere in that subtree then bubbles back up as soon as that recursive call returns.

4b. Using depth-4 search from the Tic-Tac-Toe initial state: 

                    static evaluations
  Alpha-Beta OFF            336
  Alpha-Beta ON             123

Alpha-beta reduced the number of static evaluation from 336 to 123, so we saved 213 evaluations, or a 63.4% reduction. while both searches picked the identical move, (1,1), with the identical backed-up score (0.0333...), confirming the pruning did not change the result, only the work needed to find it.

4c. Conceptual question — correctness of pruning. At any max node, alpha is the best value the maximizer has already been guaranteed to be able to achieve somewhere else in the tree, on the path explored so far; at any min node, beta is the analogous guarantee already available to the minimizer. When exploring a min node's children and one child's value is found to be <= alpha, that min node's final backed-up value (which only ever gets smaller or equal as more children are explored, since a min node takes the minimum over its children) can never rise back above that child's value. So the min node's value is already known to be at most as good for the maximizer as an alternative the maximizer can obtain elsewhere — which means the maximizer will never choose the move leading into this min node regardless of what its remaining, unexplored children turn out to be. Pruning those children is therefore safe: exploring them could only ever lower (or leave unchanged) a value that is already not going to be selected, so it cannot change the move chosen at the root. The symmetric argument holds for max nodes and beta.

    and report the numerical score your static_eval returned for it.

5c. Limitations
    Describe at least one type of board position where your static_eval
    is likely to give a misleading score, and explain why.

5a. Feature design. static_eval (in yourID_KInARow.py) scans every possible window of length k on the board in all four line directions (horizontal, vertical, and both diagonals). For each window it counts X's and O's inside it. A window containing both X and O can never become a win for either player, so it contributes 0. A window containing a forbidden square ('-') is likewise dead and contributes 0. A window containing only one player's tokens contributes ±10^count (positive for X, negative for O) — an exponential, not linear, function of how many tokens that player already has in the window. The intuition is that a line with k-1 tokens and an open square is an immediate threat that should dominate the score far more than two separate lines with one token each, and only an exponential weighting (rather than, say, a count or a sum) produces that kind of dominance. A small secondary term adds ±0.1 per token scaled by closeness to the board's center, mainly to break ties between otherwise-equal positions in favor of central play.

5b. Concrete example. From an actual agent-vs-RandomPlayer Tic-Tac-Toe game (reproduced via a short script that replays make_move turn by turn and prints static_eval after every move), after X's second move the board was: 

  O  .  .
  .  X  X
  .  .  .

(O to move next.) static_eval returned 110.1167. This is the right order of magnitude for this position: X has two tokens in the open middle row, (1,1) and (1,2), with (1,0) still blank — a single window (the middle row) contributes 10^2 = 100 to the score. The small remainder (10.1167) comes from the centrality bonus for X's two central-ish squares plus O's single corner token working against it. The dominant 100-point contribution correctly reflects that X is one move away from winning via that row if O does not block (1,0), which is exactly the kind of near-complete-line threat the exponential weighting is designed to surface.

5c. Limitations. The window-sum approach has no notion of a "double threat" or fork: it simply adds up every window's contribution independently, so a position where two different near-complete lines for X happen to share their only blocking square (meaning O can kill both lines with a single move) is scored the same as if those two lines required two separate blocking moves. In reality the latter is a much stronger position for X (O cannot stop both), but static_eval cannot distinguish "two threats, one shared escape square for the opponent" from "two threats, two independent escape squares" — both simply sum the two windows' weights. A more accurate evaluator would need to reason about which empty squares are shared between multiple live lines, not just score each line in isolation.

The concrete bug: early on, minimax() included a "win-shortcut" — after generating a child state for a candidate move, it called winTesterForK on that child, and if the move was an immediate win it returned an extreme score right away instead of recursing further. This is good for real play (it stops the search from wasting time looking past a forced win, and correctly values it as a win rather than whatever finite number static_eval happens to produce), so it was added before the autograder tests were re-run.

Symptom: autograder.py's T4 test (plain minimax, no pruning, depth 2, using the special table-based evaluator) reported the correct move but the wrong leaf count: 9 static evaluations instead of the expected 12.

Root cause: the test state (O,O,X / X,_,_ / _,_,X) actually contains a real win inside the 2-ply search tree — if O's first move leaves (1,2) open, X can play (1,2) to complete column 2 (X at (0,2) and (2,2) already). The win-shortcut correctly detected this and returned early, skipping the evaluator call for that leaf — which is good for real play, but the autograder's reference leaf count of 12 assumes the search is expanded to the literal depth limit on every branch, with no early termination of any kind (confirmed by the autograder's own hint text: "This count does NOT depend on move ordering... call the special static evaluation function at every leaf").

Fix: added a self._check_wins flag, set to True in DEMO/COMPETITION modes and False whenever self.playing_mode == KAgent.AUTOGRADER, and gated the winTesterForK call in minimax() behind it. After that change, T4 reported exactly 12 leaf evaluations and T5 (alpha-beta) reported exactly 8, both matching the reference, while the win-shortcut optimization remained active (and still valuable) for actual gameplay.

Section 8 — Reflections & Learnings (1 pt) 
Articulate what you now understand more clearly as a result of doing
this assignment.  Some prompts to consider:

  - Did implementing minimax change how you think about game-tree
    search?  Is there anything that surprised you about how it behaves?
  - What is one connection you made between the material in this
    assignment and something else from the course or from outside it?
  - If you were to explain alpha-beta pruning to a classmate who
    had not yet implemented it, what is the single most important
    thing you would tell them?

Implementing iterative deepening under a wall-clock budget changed how I think about game-tree search: instead of "minimax to depth N," it is more natural to think of it as an anytime process that produces an improving sequence of answers, where each depth's result is only trustworthy if that whole depth finished before the clock ran out (which is why the agent only adopts a depth's result after that depth's top-level call returns, catching a timeout exception rather than trying to salvage a half-finished depth). The surprising part was how much a single optimization (the win-shortcut in Section 7) could clash with a grading reference's implicit assumptions — "correct and fast" and "matches the expected leaf count" turned out to be two different properties, and only one of them was actually being tested.

The most useful connection to make is to the alpha-beta measurement in Section 11 (Extra Credit): fewer nodes visited is not automatically faster in wall-clock time if the per-node work (here, calling static_eval to order children) is expensive relative to what it saves. That is the same lesson taught more abstractly in discussions of asymptotic complexity vs. real performance — Big-O node counts and actual runtime can diverge once you account for the constant factors.

If I were explaining alpha-beta to a classmate who had not implemented it yet, the one thing I would say is: the bound you are pruning with (alpha at a max node, beta at a min node) is not a property of the subtree you're currently searching — it is a guarantee from somewhere else in the tree that the player who owns that bound already has in hand. You're not saying "this subtree is bad"; you're saying "it doesn't matter whether this subtree is bad, because nobody would ever choose to go here anyway."

Part I-A: Child ordering by static evaluation

In DEMO/COMPETITION modes, _generate_moves_ordered builds the child state for every candidate move and sorts the candidates by static_eval of that child before recursing: descending for X (the maximizer, so the move most favorable to X is tried first) and ascending for O. The intent is the classic alpha-beta result that searching the best move first maximizes the chance that later siblings can be cut off by the current alpha/beta bound.

Measurement. extra_credit_benchmark.py runs a fixed 4-ply alpha-beta search from the Cassini initial state (chosen because its two handicap O's give the candidate-restricted move generator something to work with from move 1) with and without this ordering: 

              nodes visited   cutoffs (rate)     leaf evaluations
  baseline         3730       3197  (85.7%)           30920
  ordering         1097        984  (89.7%)            3309

Ordering by static eval cut the number of search-tree nodes visited by about 71% (3730 → 1097) and the number of true leaf evaluations by about 89% (30920 → 3309), while the per-node cutoff rate also rose slightly (85.7% → 89.7%). Both configurations picked the same move, as expected since alpha-beta is exact regardless of ordering.

What I learned. The tree-size reduction was far larger than I expected, but it did not translate into a faster wall-clock move in this implementation: ordering requires computing static_eval for every candidate at every internal node it visits (33018 extra "ordering" evaluations here), and because static_eval scans every k-length line on the board, that overhead is roughly as expensive as the leaf evaluations it saves. The lesson is that move-ordering heuristics need to be cheap relative to the thing they are trying to avoid recomputing — a full static evaluator is a sound, pedagogically clear choice (and is what the assignment asked for), but a production engine would want a much cheaper ordering signal (e.g. a shallow pattern/neighbor count) to actually convert the smaller tree into a wall-clock win, or cache the static evals so they are not recomputed on overlapping subtrees (see Part I-B).

Part I-B: Zobrist hashing

Zobrist hashing assigns one independent random 64-bit number to every (square, piece) pair on the board (plus one for "it is X's turn" and one for "it is O's turn"), computed once in _init_zobrist when prepare learns the board size. A state's hash is the XOR of the numbers for every occupied square plus the side-to-move number (_zobrist_hash). XOR makes the hash order-independent and cheap to verify, and two different move orders that reach the same board (a transposition) hash identically, so a transposition table keyed by this hash lets the search recognize "I have already solved this position at this depth" and reuse the stored result instead of re-searching it.

Every table access goes through two small helpers, _tt_read/_tt_write, which keep three counters: writes (every time a node's backed-up value is stored), read attempts (every lookup, hit or miss), and successful attempts/hits (lookups that found a previously stored entry). Those three numbers are returned in the AUTOGRADER-mode stats dict as zobrist_table_num_entries_this_turn, zobrist_table_num_reads_this_turn, and zobrist_table_num_hits_this_turn. A hit is only used to short-circuit the search directly when not using alpha-beta pruning and the cached depth is at least the depth remaining (otherwise the cached value could be a pruned bound rather than the exact backed-up value, and reusing it could be unsound); as the extra-credit option notes, cached values are also used to help order children (Part I-A) — a child whose value is already in the table is scored from the cache instead of calling static_eval again.

Measurement. Same 4-ply Cassini benchmark, with Zobrist hashing turned on: 

              tt writes   tt read attempts   tt hits (successful)
  zobrist        3730           3730               810
  both           1097          34115               383

With plain minimax node ordering ("zobrist" row, no I-A ordering), every node is visited exactly once per the usual tree shape, so writes equal read attempts (3730 each) and about 22% of reads (810/3730) found a transposition from elsewhere in the same search. Combined with I-A ordering ("both" row), far fewer nodes are backed up and written (1097), but _ordering_eval adds a read attempt for every candidate at every node it visits (34115 reads total), of which 383 were reused instead of calling static_eval again.

What I learned. Transpositions are genuinely common in this game even over a short 4-ply search (hundreds of hits), which matches the intuition that K-in-a-Row has many move orders reaching the same board. However, because my transposition table is only safe to use for a direct cutoff in the no-pruning case, most of its value here came from the ordering use case rather than the raw node-skipping use case — a more sophisticated implementation would store alpha/beta bound flags (exact/lower/upper) with each entry so cached values could also be used safely to narrow the window under alpha-beta pruning, not just to order children.

Part II: LLM-assisted dialog (Claude, via the Anthropic SDK)

prepare() only imports anthropic when self.playing_mode == KAgent.DEMO and utterances_matter is true, exactly as the assignment specifies, and the import plus client construction are wrapped in a try/except that leaves self._llm_client as None on any failure. The API key is read from the ANTHROPIC_API_KEY environment variable rather than hard-coded in the file. Why: this repository is public on GitHub, and a hard-coded key in a public repo gets scraped by automated bots within minutes of pushing — unlike a free-tier Gemini key, an Anthropic key is billed by default with no inherent spend cap, so the downside of a leak is an unbounded bill rather than just rate-limiting. Every call site that actually talks to the API (_llm_reply, used by both _llm_commentary for ordinary per-turn lines and _llm_story for the "what's your take" feature) is also independently wrapped in a try/except Exception and returns None on any failure, at which point _generate_utterance falls back to the rule-based KITTI_LINES bank or template, so the agent never raises and never stalls waiting on a hung request. A time-budget guard (_llm_time_budget_ok) also skips the LLM call entirely once more than 1.6s of the move has already been spent or less than 1.0s remains before the search deadline, so a slow network can never push a DEMO-mode move past the "no more than 3 sec" guidance.

Verification (no real key available in this environment). I could not end-to-end test an actual Claude response from this sandbox, but I directly verified every failure path the assignment specifically warns about, by running make_move under each condition and confirming the agent kept playing with a valid, non-empty, in-character utterance every time: 

  SDK not installed (ModuleNotFoundError on `import anthropic`):
      prepare() -> 'OK', self._llm_client is None, move proceeds normally.
  ANTHROPIC_API_KEY set to a fake/invalid value, SDK missing:
      prepare() -> 'OK', self._llm_client is None, move proceeds normally.
  playing_mode == COMPETITION, utterances_matter=False:
      prepare() -> 'OK', self._llm_client is None (import never attempted),
      utterance -> 'ok.'

What I learned. Writing the fallback-safety code was almost all of the actual effort here — the "happy path" API call is a few lines, but making sure three independent kinds of failure (missing package, missing/bad key, slow network) all degrade to the same safe behavior took real design thought (gating at import time and at call time, plus a time budget separate from the search's own deadline). I'd recommend testing these failure paths explicitly rather than assuming "it'll just except out fine" — it's easy to leave one path (e.g. a hung request with no client-side timeout) that doesn't actually fail fast.
